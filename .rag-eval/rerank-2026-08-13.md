# CodePilot Cross-Encoder Rerank 实验（2026-08-13）

> 结果来自 30 条开发集，已用于方案选择，不能当作独立冻结测试集或最终简历指标。

## 实现方案

```text
BM25 Top-90 ─┐
              ├─ Weighted RRF Top-30
Vector Top-90 ┘          ↓
              Cross-Encoder(query, chunk)
                         ↓
                    最终 Top-10
```

- 模型：`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`
- 选择原因：支持多语言，比 BGE-v2-m3 更适合当前本地 CPU 原型的资源边界。
- 候选内容：文件路径、起止行和 Chunk 正文。
- 最大长度：512 Token；256 Token 实验会使指标类查询的正确实现掉出 Top-10，因此未采用。
- Batch：16；32 在当前 CPU 上更慢，因此保留 16。
- 模型懒加载、进程内复用，predict 使用锁保护并发模型访问。
- 在线查询仅使用本地缓存；模型缺失/推理失败时回退 RRF，并标记 `rerank_fallback`。

## 开发集结果

| 方法 | Recall@10 | MRR | 预热后 Avg | P95 | 回退率 |
|---|---:|---:|---:|---:|---:|
| BM25 | 0.7806 | 0.5664 | 37.5 ms | 49.1 ms | 0% |
| Vector | 0.4611 | 0.3496 | 55.3 ms | 68.0 ms | 0% |
| Hybrid | 0.8139 | 0.5776 | 77.4 ms | 86.8 ms | 0% |
| Cross-Encoder Rerank | **0.9833** | **0.7426** | **3424.4 ms** | **3761.8 ms** | **0%** |

相对 Hybrid，Rerank 在本开发集上的 Recall@10 绝对提高 0.1694，MRR 绝对提高 0.1650，但平均增加约 3.35 秒预热后查询延迟。这是明显的质量—延迟交换。

## 冷启动与部署

- 本机首次模型下载受网络影响约 8.5 分钟，只发生一次。
- 模型已有本地缓存后，新进程加载仍约 25～47 秒；服务部署应在 readiness 前预热。
- 模型缓存在项目 `.codepilot/model-cache`，不会依赖无写权限的用户缓存目录。
- 显式准备命令：`python -m rag.reranker --download`；只检查缓存：`python -m rag.reranker`。
- CPU 并发下 Cross-Encoder 是瓶颈；当前使用进程内锁保证正确性，生产环境应考虑独立推理服务、GPU 或受控并发队列。

## 是否适合默认启用（独立复核后修订）

复核发现上表复现依赖未更新的索引与精确旧行号标签；在最终工作树重建索引并让行号区间标签容忍主要区间重叠后，Rerank 为 Recall@10 0.9250、MRR 0.7033、平均 7711.7 ms、P95 9094.7 ms。它仍优于 Hybrid 的 Recall@10 0.8139、MRR 0.5574，但收益来自已参与模型选择的 30 条开发集，并存在 `CP-B04` 从 Hybrid Top-3 掉出 Rerank Top-10 的真实退化。新进程模型加载复测为 49.5～50.5 秒。不同轮次的 Rerank 平均延迟在 3.28～7.71 秒间波动，CPU 稳定性不足。

因此 CPU 默认改为关闭；高质量部署可显式开启并在 readiness 前预热。以下场景尤其应保持关闭：

- 交互式搜索对亚秒延迟敏感。
- 模型未预热且不允许冷启动等待。
- 高并发 CPU 服务。
- 已知查询以精确标识符为主，此时 BM25 已是强基线。

开启方式：`rag.reranker.enabled=true`。关闭时仍保留 BM25 + Vector + RRF，不影响基础检索；离线评测显式使用 `mode=rerank`，不受默认开关影响。

## 有效性边界

- 评测集只有 30 条且已经参与参数与模型选择，存在过拟合风险。
- 正式简历数字必须在新的冻结测试集上复核。
- 当前只评估检索指标，尚未评估最终 Agent 代码修改成功率。
- 当前模型不是代码专用 Reranker；后续可在相同冻结集上比较 BGE/BCE 或代码领域模型。
