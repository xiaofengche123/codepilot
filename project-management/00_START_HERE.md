# CodePilot 项目管理中心

> 这是 CodePilot 后续开发的统一入口。无论是项目本人还是新 AI，在开始修改代码前都应先阅读本文件。

## 1. 项目目标

CodePilot 的目标不是做一个简单的聊天壳或只会向量检索的 RAG Demo，而是建设一个可解释、可验证、可安全执行代码修改的本地 Coding Agent 平台。

目标能力闭环：

```text
任务分析
  → 检索策略选择
  → BM25 / Vector / Weighted RRF / 条件式 Rerank
  → 形成代码证据
  → 制定修改计划
  → 安全、事务式编辑
  → 运行目标测试
  → 失败分析与恢复
  → Diff 审核
  → 输出结果与 Trace
```

项目追求的是有依据的工程复杂度：每个新增模块必须解决已测量的问题，并具有测试、失败处理、回退策略和评测证据。禁止为了简历堆砌没有使用场景的 Graph RAG、Multi-Query 或其他名词。

## 5. 状态标识

所有任务统一使用以下状态：

| 状态 | 含义 |
|---|---|
| `DONE` | 已实现、已验证且已有结果 |
| `IN_PROGRESS` | 当前正在实现，可能存在未提交改动 |
| `NEXT` | 下一阶段应优先执行 |
| `PLANNED` | 已确定需要做，但有前置依赖 |
| `BLOCKED` | 有明确阻塞条件，必须记录原因 |
| `IDEA` | 尚未证明价值，不得直接实施 |
| `REJECTED` | 已有证据表明当前不应实施 |

## 6. 当前优先级

### P0：保护与固化当前成果

- 审查当前未提交改动。
- 确认正式结果、冻结集和报告完整。
- 确认 `.codepilot/model-cache`、外部原始数据、临时 worktree 未进入提交。
- 在用户确认后提交到 `dev`，不要直接覆盖 `master`。

### P1：提高 Agent 代码修改成功率

- 实现事务式局部编辑工具。
- 增加路径隔离、前置 SHA、原子写入、语法验证和失败回滚。
- 在现有20个端到端任务上验证目标文件修改率和任务成功率。

### P2：建立执行状态机和阶段 Trace

- 将 Agent 行为拆为检索、阅读、计划、编辑、验证、恢复、审核。
- 记录每个阶段的客观工具事件和失败原因。
- 减少“已经找到文件但10步耗尽仍未修改”的情况。

### P3：自适应检索

- 保留现有四种检索模式。
- 根据查询类型、两路排名一致性和延迟预算选择权重及是否精排。
- 只能在开发集调参，不能用冻结 test-v1 调参。

### P4：代码结构图扩展

- 先支持 Python AST 的 imports/calls/contains/tests 关系。
- 只作为混合检索后的结构扩展，不替换 BM25 和 Vector。
- 必须在跨模块专项评测中证明收益后才能默认使用。

## 7. 每轮开发完成标准

一次工作只有同时满足以下条件才算完成：

- 实现符合任务范围，没有顺带重写无关模块。
- 新增或更新了对应测试。
- 运行目标测试，并按风险运行全量测试。
- 执行 `git diff --check`。
- 没有修改冻结测试答案来优化数字。
- 没有提交模型缓存、外部原始数据、临时目录或密钥。
- 更新 `03_PROGRESS_TRACKER.md`。
- 在 `08_SESSION_LOG.md` 增加本轮记录。
- 如果做出新架构决策，更新 `05_ARCHITECTURE_AND_DECISIONS.md`。

## 8. 给 AI 的最短指令

如果用户只说“继续做 CodePilot”，AI 应当：

1. 阅读本文件和 `03_PROGRESS_TRACKER.md`。
2. 查看 `git status --short`，保护所有未提交改动。
3. 阅读最近一条 `08_SESSION_LOG.md`。
4. 选择状态为 `NEXT` 且依赖已满足的最高优先级任务。
5. 先审查和复现，再实现；完成后测试并更新文档。
